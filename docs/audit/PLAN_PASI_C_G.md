## Pasul D — Reutilizarea persoanelor
- **Model real:** un rând `concesionari` poate avea mai multe `contracte`, fiecare cu alt `id_loc` ⇒ **aceeași persoană la mai multe locuri este deja posibilă la nivel de date**; `contracte` păstrează `owner_*` ca instantaneu. Cererile online (`shared/cimitir_requests.py:111`) reutilizează concesionarul prin CNP exact. Mobile are selecție de concesionar în formularul de contract (registrul generează câmpul de tip relație). Înhumații sunt înregistrări legate de un singur loc (nu există „persoană” înhumată reutilizabilă).
- **Lipsește:** căutare/selectare explicită în MAIN și Mobile cu previzualizare, avertizare la posibil duplicat (reguli deja formulate în `CON004–CON007`: CNP identic; nume+telefon/e-mail/adresă; **niciodată doar nume**), garanția că sincronizarea nu creează un al doilea rând pentru aceeași persoană (v2 folosește `uid`; cererile pe baza CNP exact pot crea duplicate dacă CNP lipsește).
- **De clarificat de dumneavoastră:** „persoane” = doar concesionari (vii) sau și înhumați (aceeași persoană înhumată de două ori nu are sens; se tratează ca eroare `INH008`)?
- **Fișiere:** `desktop/contracts_window.py` (+ dialog de căutare), `desktop/*concesionar*`, `shared/cimitir_requests.py`, `shared/cimitir_mobile_registry.py`, `backend/static/mobile_app.js`/`mobile_ext.js`. **Migrații:** probabil niciuna (eventual index pe hash de CNP — doar cu aprobare, vezi §CNP). **Riscuri:** căutarea după CNP în Mobile expune date de identitate (se respectă permisiunile pe câmp din 027); contopirea automată este exclusă. **Test:** unitare pe regulile de potrivire, sincronizare MAIN↔Cloud↔Mobile cu aceeași persoană la 2 locuri fără multiplicare. **Complexitate: M–L.**

## Pasul F — Fișa unificată a locului
- **Realitate financiară (citită din cod):** există doar `plati`. **Nu există obligații de plată, scadențe, tarife sau sold în schemă**; `total_plati` este suma plăților; nu există stare „anulat” (doar ștergere) și nu există câmp de stornare (sumă negativă posibilă în MAIN, respinsă în Mobile). **Nu voi inventa o formulă de sold.** Propunere: etapa 1 afișează *Total încasat* (suma plăților, cu menționarea limitei) și lista plăților; **soldul** devine posibil doar după ce definiți ce este o obligație (ex. taxă de concesiune pe contract) — decizie de business + migrare nouă.
- **Istoric pe câmp:** *legacy* `audit_log` păstrează `old/new` pe câmp (portalul îl afișează în `entity_history`), dar **v2 (`sync_v2_ops`) păstrează doar acțiune/stare/dispozitiv/moment, nu valorile**. Utilizatorul și originea (`device_type`: MAIN/Mobile) sunt disponibile unde există; „Cloud” ca origine nu este înregistrat explicit. Evenimentele nerecordate nu se inventează; fișa va marca „istoric indisponibil înainte de data X”.
- **Fișiere:** nou `shared/cimitir_fisa_loc.py` (agregare doar-citire), `desktop/` (fereastră/fișă), API read-only în `backend/`, Mobile (`mobile_app.js`). **Migrații:** niciuna pentru etapa 1; **da** pentru obligații/sold și pentru stocarea valorilor vechi/noi în v2 (necesită aprobare separată + analiza impactului MAIN/Cloud/Mobile/versiuni vechi). **Riscuri:** F-02 (CNP în `audit_log`) trebuie rezolvat înainte de a afișa istoric cu valori; confuzie sold vs. total încasat. **Test:** agregare pe date sintetice, comparare cu `verificare_evidente`. **Complexitate: L.**

## Protecția CNP/CI — constatări (audit; **nicio criptare nouă, niciun format schimbat, nicio migrare**)
- **Stocare:** `cnp`/`bi_ci` (și `owner_cnp`, `owner_id_card_serie_number`) sunt text în clar în SQLite și PostgreSQL (nu am găsit `pgcrypto`/criptare în migrări).
- **Transmitere:** prin HTTPS către Cloud; Mobile respectă permisiuni pe câmp (migrarea 027, PR #30).
- **Loguri/audit:** *legacy* `audit_log.detail` conține CNP/CI **în clar** (F-02, verificat). Nu am găsit `print`/`logger` care să scrie CNP; audit complet al excepțiilor/mesajelor de eroare nu a fost încă făcut exhaustiv.
- **Exporturi/PDF:** CNP apare intenționat în contracte/adeverințe (`pdf_reports.py`); alte exporturi neauditate exhaustiv.
- **Îmbunătățiri propuse (compatibile):** (1) adăugarea `cnp|bi_ci|owner_cnp|owner_id_card…` în `_SENSITIVE` din `audit_entities.py` (mascare la scriere; fără modificarea formatului datelor) + test; (2) mascarea CNP în afișările de listă; (3) verificare că mesajele de eroare ale API nu repetă payload-ul; (4) **separat și doar cu aprobare:** redactarea înregistrărilor istorice deja scrise în `audit_log`, și o eventuală criptare/hash.

## Testarea sincronizării complete (MAIN ↔ Cloud ↔ Mobile) — plan
Matricea: entități {locuri, concesionari, contracte, înhumați, avize, plăți, documente, fotografii} × scenarii {creare, modificare, ștergere/arhivare, resincronizare, offline→reconectare, conflict între dispozitive, eroare de rețea+retry, permisiuni insuficiente, versiune veche de client, documente atașate}. Metodă: mediu **local izolat** (PG efemer + Cloud local + MAIN offscreen + Chromium), date sintetice; pentru fiecare caz verificare a **stării din baza de date** (nu doar HTTP 200): număr de rânduri, valori câmp cu câmp, absența duplicatelor, versiuni. Acoperire existentă: replay idempotent, conflicte, permisiuni, coadă offline PWA și migrarea 028 (vezi raport). **Nu declar sincronizarea „completă” — F-01 arată un caz real (formatul datei) care trece HTTP 200 dar pierde date.**
